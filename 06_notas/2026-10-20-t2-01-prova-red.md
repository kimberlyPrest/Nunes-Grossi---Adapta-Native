# T2.01 — Prova RED (baseline antes da correção)

**Data:** 20/10/2026 · **Task:** T2.01 · **SPEC:** SPEC-1-002 · **Base auditada:** commit `afe8fff` (v0.0.13), pós-T1.02

## Comportamento observado hoje (análise de código; o banco real só é acessível à Louise no projeto da N&G)

Desativar um usuário hoje grava apenas `profiles.situacao = 'inativo'`. Nada muda em `auth.users`:

1. `supabase/functions/admin-users/index.ts` (ação `toggle_status`): único efeito é
   `update({ situacao })` em `public.profiles`. Sem ban, sem revogação de sessão.
2. `src/services/usuarios.ts` (`toggleUserStatus`, fallback do frontend): mesmo efeito, direto no
   banco via RLS.
3. Consequência: o usuário inativo continua conseguindo **autenticar** (GoTrue não tem
   `banned_until` gravado) e recebe um JWT válido; as chamadas dele passam a falhar só onde a RLS
   usa `is_active_user` (oportunidades e tabelas dependentes) — leituras de catálogo, clientes e
   equipes continuam permitidas a qualquer autenticado.
4. O bloqueio que existe é só no frontend: `src/hooks/use-auth.tsx` (signIn desloga se o perfil
   vier inativo) e `src/components/ProtectedRoute.tsx` (redireciona se `situacao = 'inativo'`).
   Não protege contra chamada direta à API nem contra sessão já aberta em outra aba.

## Falha esperada registrada (RED)

**CA-1-08 falha hoje no critério de banco:** "usuário desativado não consegue entrar" não é
garantido pelo servidor — o login do inativo continua funcionando; a tela é que esconde o sistema.

## Correção aplicada (resumo, detalhes no mapa do tronco)

Trigger no banco `handle_situacao_login_ban` (migração `20261020110000_t201_bloqueio_inativo.sql`):
ao gravar `situacao = 'inativo'`, grava `banned_until` em `auth.users` e revoga os refresh tokens
(a sessão aberta não renova); ao gravar `'ativo'`, remove o ban. Vale para qualquer caminho que
mude a situação: edge function `admin-users`, fallback do frontend ou SQL direto.
