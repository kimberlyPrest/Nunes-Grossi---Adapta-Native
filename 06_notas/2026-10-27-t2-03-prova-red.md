# T2.03 — prova RED (Storage ignora a oportunidade)

**Data:** 27/10/2026 · **Task:** T2.03 · **SPEC:** SPEC-1-002 · **Critério:** CA-1-06 (parte documentos)

## O que está sendo testado

O arquivo anexo de uma oportunidade só pode ser baixado por quem pode **ver a oportunidade**.
O objeto do Storage (`storage.objects`, bucket `oportunidades-anexos`) é a segunda barreira: a
primeira é a tabela `oportunidades_documentos`, já corrigida na T2.02.

## Baseline RED — o estado atual, verificado no código

As quatro políticas do bucket, criadas na migração `20261016233000_ficha_oportunidade_extensions.sql`
(linhas 121–155), têm **todas** o mesmo predicado:

```sql
USING (bucket_id = 'oportunidades-anexos' AND public.is_active_user(auth.uid()))
```

Não há `pode_ver_oportunidade` em nenhuma delas. Consequências, por caminho:

| Caminho | Hoje | Deveria |
|---|---|---|
| `SELECT` em `storage.objects` (listar) | Qualquer usuário ativo vê todos os objetos do bucket | Só quem vê a oportunidade |
| `createSignedUrl(path)` | Qualquer usuário ativo, com o caminho, gera link válido por 1h | Só quem vê a oportunidade, link curto |
| `INSERT` (upload) | Qualquer usuário ativo envia para qualquer oportunidade | Anexar exige poder ver a oportunidade (decisão de Pedro, 27/10 13:49) |
| `DELETE` | Política permite apagar o objeto | RN-06: nada é excluído |

**Por que isso fura o CA-1-06:** o critério exige que o colaborador de Seguros não baixe documento
de Saúde. A tabela de metadados nega (T2.02), mas o arquivo em si é alcançável por
`createSignedUrl` direto no SDK, sem passar pela tabela. O caminho não é segredo: é
`{oportunidade_id}/{etapa_id}/{item}_{timestamp}_{nome}`, e o `oportunidade_id` aparece em qualquer
tela do usuário.

## Por que não foi pego antes

O teste 2 (CA-1-06) pulou o passo 5 porque **não havia documento anexado** no ambiente. O furo
estava escondido atrás de um fixture ausente, não atrás de uma lógica correta.

## Verificação de confirmação (para rodar no SQL editor, papel `authenticated`)

```sql
BEGIN;
SET LOCAL ROLE authenticated;
SET LOCAL request.jwt.claims = '{"sub":"<uuid-do-colaborador-seguros>","role":"authenticated"}';
-- RED: hoje isto devolve os objetos do bucket, inclusive de oportunidades que ele não vê
SELECT count(*) AS objetos_visiveis FROM storage.objects WHERE bucket_id = 'oportunidades-anexos';
ROLLBACK;
```

## GREEN esperado

O mesmo `SELECT` devolve **0** (ou apenas os objetos das oportunidades dele), porque o predicado
passa a exigir `pode_ver_oportunidade(oportunidade_do_caminho(name), auth.uid())`.
